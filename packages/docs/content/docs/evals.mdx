An eval case is a Markdown file that says what a run should do, plus a script of steps that Plico
replays against your project. Replaying needs no model and no API key, so it is a good gate in CI.
Scripted evals check your wiring: the tools exist, the approval rules hold, the run ends how you
expect, the output has the right fields. To see what the model actually does, run the same cases
with [`plico eval --live`](#live-runs).

```bash
plico eval .
```

```text
Eval results for .
  PASS refund-approved (eval-refund-approved-5fb6d184)
  PASS refund-denied (eval-refund-denied-12aad571)
       Approval for issue_refund was denied.
  PASS refund-held (eval-refund-held-5607f9f4)
  SKIP vpn-outage: No .script.json fixture; runs with --live.

3/3 passed, 0 failed, 1 skipped
```

`plico eval` exits 0 when every case passes and 1 when a case fails. It also exits 1 when no case
ran, so a CI gate cannot pass with nothing tested. `--allow-empty` accepts an empty `evals/` folder.

## The case file

Each `evals/<name>.md` is one case. The frontmatter says what to check; each bullet in the body is a
criterion for a judge model.

```md
---
expect:
  status: completed
  contains: Refunded
  tool: issue_refund
  notTool: send_email
  output:
    orderId: A-1001
tags: [regression]
---
- Confirms which order was refunded
- Does not promise a delivery date
```

`evals/<name>.script.json` next to it holds the steps scripted mode replays. A case without one is
skipped by `plico eval` and listed as `SKIP`; it still runs with `--live`.

| Key | Meaning |
| --- | --- |
| `expect` | Code checks over the whole run. See below. |
| `input` | What the agent receives in a live run. Checked against `agent.md`'s `input` schema; without a schema, text is sent as the message. |
| `mocks` | Fixed results for named tools in live runs, such as `create_ticket: { id: T-1 }`. |
| `trials` | How many live runs the case gets. Defaults to 1. |
| `tags` | Labels such as `regression`. |
| `judge` | The judge model for this case's criteria, as `provider:model`. |
| `scorers` | Custom scorers by name, see [Custom scorers](#custom-scorers). |

`plico validate` checks every case and points at the line, such as
`evals/refund.md:4: Unknown key "expect.contian"`, so a typo fails before anything runs.

## Expect

| Check | Passes when |
| --- | --- |
| `status` | The run ended `completed`, `waiting`, `failed` or `cancelled`. Without it, the run must complete. |
| `contains` | The final output contains this text. |
| `tool` | Each named tool was called. A name or a list. |
| `notTool` | None of the named tools was called. |
| `artifact` | Each named artifact file was written. |
| `output` | Each field matches the run's `structuredOutput`. Nested objects match the fields they list. |
| `maxTokens` | The run used at most this many tokens. Live runs only. |
| `maxLatencyMs` | The run took at most this many milliseconds. Live runs only. |

In scripted mode, `maxTokens`, `maxLatencyMs` and the body's criteria are reported as skipped and do
not fail the case: a script makes no model calls, and grading a script would only grade the fixture.
In live mode the budgets apply. Criteria are still reported as skipped until the judge ships.

## Live runs

`plico eval --live` sends each case's `input` to the configured model, the way
`plico run --input` does, and runs the same `expect` checks and scorers on the result. It needs a
model and its key in `plico.config.ts` and `.env`. A case without `input`, and a fixture on its own,
is listed as `SKIP`. Live runs are not stored as the project's eval report, so
`plico readiness` keeps reporting the scripted results.

<Callout type="warn">
  Tools run for real in live mode unless the case mocks them. A tool that sends email or creates a
  ticket does so on every live run.
</Callout>

Two ways keep tools from running:

- **`mocks`** in the case gives a fixed result for each named tool, on every call:

  ```yaml
  input: VPN is down for the whole sales team
  mocks:
    create_ticket: { id: T-1 }
  ```

- **`--mock-tools`** takes every tool result from the case's `.script.json`, in order for each tool.
  A call with no result left fails, and the model sees the error. A `"live": true` step runs that
  call's handler. `mocks` still wins over the fixture.

Approval policy applies as in a run. Nobody approves during an eval, so a tool that needs approval
leaves the run `waiting`; expect that with `status: waiting`.

| Option | Meaning |
| --- | --- |
| `trials: n` in the case | Runs the case n times. It passes only when every trial passes, and the result shows how many did, such as `2/3 trials passed.` |
| `--model <provider:model>` | Runs the suite on another model, so comparing two models is two commands. |
| `--max-tokens <n>` | Caps the tokens of the whole suite. A model call starts only if it and the calls already running, each counted at the average call so far, fit under the cap. Once a call is refused, no case or trial starts, the rest (and any run cut off) are listed as `SKIP`, and `plico eval` exits 1. A single call can still use more than the average. |
| `--concurrency <n>` | Live runs at once. Defaults to 4. |

## Custom scorers

A scorer is a TypeScript file in `evals/scorers/` that sees the whole run and returns a score from 0
to 1 with an optional reason:

```ts title="evals/scorers/no-pii.ts"
import { defineScorer } from "@plico-ai/sdk";

export default defineScorer({
  name: "no-pii",
  score: ({ output }) => ({
    score: /\b\d{3}-\d{2}-\d{4}\b/.test(output) ? 0 : 1,
    reason: "Output contains a social security number",
  }),
});
```

A case names it under `scorers`. It passes at a score of 1 unless the entry sets a `threshold`:

```yaml
scorers: [no-pii, { use: tone, threshold: 0.8 }]
```

The scorer receives `output`, `structuredOutput`, `status`, `events` (every tool call, artifact and
model response of the run), the case's `input`, and its `expect` block as `expected`.

## The script

The steps are the same ones `plico run --dry --script` takes, so you can try a case on its own:
`plico run --dry --script evals/refund-approved.script.json .`.

| Step | Fields |
| --- | --- |
| `assistant.output` | `content`, the text the agent says. With an `output` schema, JSON text becomes `structuredOutput`. |
| `tool.call` | `toolName`, `arguments` and `result`. |
| `approval.decide` | `approved`. Right after a `tool.call` that needs approval. |
| `artifact.write` | `files`, each with `path`, `content` and an optional `mimeType`. |

Evals never run tool handlers by surprise. A `tool.call` step supplies the tool's output as
`result`, and the run uses it instead of calling the handler. A step without `result` fails the case
and names the tool. Add `"live": true` to run the real handler on purpose. Arguments are still
checked against the tool's `inputSchema`.

### A fixture on its own

A `<name>.script.json` with no `<name>.md` beside it is a case of its own, the format earlier
versions used. It is either the array of steps or an object:

```json
{
  "description": "A person approves the refund and the agent confirms it.",
  "script": [{ "type": "assistant.output", "content": "Refunded order A-1001." }],
  "expect": { "status": "completed", "outputContains": "Refunded" }
}
```

Its `expect` takes the same checks as the Markdown case, and `outputContains` is the same as
`contains`. A new project ships one such case, `evals/smoke.script.json`.

## Test approvals

Approval policy applies in evals as it does in a run. Three cases cover a tool that needs approval:

- **Held.** No `approval.decide` step. The run stops as `waiting` and the tool never runs. Use
  `expect: { status: waiting }`.
- **Approved.** `{ "type": "approval.decide", "approved": true }` right after the tool call. The run
  records `approval.requested` and `approval.decided`, uses the step's `result` and carries on.
- **Denied.** `"approved": false` ends the run as `failed` before the tool runs. Use
  `expect: { status: failed }`.

An `approval.decide` step that does not follow a tool call needing approval fails the case. See
[Approvals](/docs/approvals).

## Turn a run into a case

`plico eval --from-run <run-id> [--name <name>] [path]` writes a stored run as `evals/<name>.md` and
its `evals/<name>.script.json` fixture (the name defaults to the run id). Each tool call keeps the
output it produced as `result`. `expect` records the run's status and its structured output, or its
final text as `contains`. Add criteria as bullets afterwards. It refuses to overwrite an existing
case and fails on an unknown run id. Files a tool wrote are not carried over.

For a complete project with three cases, see [Example: a refund agent](/docs/refund-agent).
