Tools are loaded from their `.tool.ts` files. They can import sibling TypeScript
modules and npm packages installed in the project. `create-plico` includes a
`package.json` with `type: "module"` for ESM tool imports.

Wrap a tool in `defineTool` from `@plico-ai/sdk` to get editor types. `defineTool` infers the
handler `input` from `inputSchema` and returns its argument unchanged.

```ts title="tools/add.tool.ts"
import { defineTool } from "@plico-ai/sdk";
import { z } from "zod";

export default defineTool({
  name: "add",
  description: "Add two numbers.",
  inputSchema: z.object({ a: z.number(), b: z.number().default(0) }),
  capabilities: [],
  approval: { required: false },
  handler: ({ a, b }) => a + b,
});
```

## Fields

| Field | Meaning |
| --- | --- |
| `name` | The name the model calls. Unique across the project; `list_files`, `read_file`, `write_file`, `edit_file` and `load_skill` are reserved. |
| `description` | Tells the model when to use the tool. |
| `inputSchema` | Zod or JSON Schema for the arguments. |
| `capabilities` | Required list of labels for what the tool touches, such as `["ticket:write"]`. Plico records it in `tools.discovered` and does not enforce it. |
| `approval` | Required. `{ required: true, reason }` holds each call for a person. See [Approvals](/docs/approvals). |
| `handler` | `(input, ctx)`. `input` is the parsed arguments; `ctx` has `artifacts`, `context`, `signal` and an idempotency key. |

A tool must export its definition as the file default.

## MCP configuration (in progress)

[MCP support](https://github.com/ITZSHOAIB/plico/issues/77) includes typed
configuration, offline validation, explicit runtime discovery, tool execution
through the run loop, readiness connectivity diagnostics and Studio inspection.

Declare sources in `plico.config.ts` with an explicit transport and tool allowlist:

```ts title="plico.config.ts"
import { defineConfig } from "@plico-ai/sdk";

export default defineConfig({
  schemaVersion: 1,
  name: "Support agent",
  mcpServers: {
    tickets: {
      transport: "stdio",
      command: "node",
      args: ["./integrations/tickets.mjs"],
      env: ["TICKETS_TOKEN"],
      tools: ["get_ticket"],
      callTimeoutMs: 10_000,
    },
    docs: {
      transport: "streamable-http",
      url: "https://mcp.example.com/mcp",
      headersEnv: { Authorization: "DOCS_AUTHORIZATION" },
      tools: ["search"],
    },
  },
});
```

Server ids use lowercase letters, digits and underscores, starting with a letter.
`tools` is required: exact server tool names, unique and non-empty, with no wildcard
patterns. An empty list exposes no tools. Newly advertised tools will require an
allowlist change.

For stdio, `command` names an executable; `args` is an optional string array.
The stdio working directory is the project root.
`env` lists host environment variable names to pass to the server, not their values.
For Streamable HTTP, `url` must be an absolute HTTP(S) endpoint without embedded
credentials or a fragment. `headersEnv` maps HTTP header names to host environment
variable names. It rejects transport-managed headers case-insensitively: `Mcp-Session-Id`,
`Mcp-Protocol-Version`, `Content-Type`, `Accept`, `Host`, and `Content-Length`.
For example, `DOCS_AUTHORIZATION` will hold the complete
`Bearer …` value. Environment values will be resolved when connecting, not during
project loading. Keep credentials out of URLs, arguments and config literals.
OAuth flows are deferred.

`callTimeoutMs` is an optional positive 32-bit integer (default `30_000`) for the
entire execution connect/list/call sequence. It does not change explicit discovery's
separate `timeoutMs` option. `replayOnCrash` optionally lists exact allowlisted tool
names whose interrupted calls may be repeated during recovery; it defaults to `[]`.

`plico validate` checks these shapes without launching a server, making network
requests or requiring environment variables to be set. It rejects unknown fields
and fields from the wrong transport. Explicit runtime discovery checks connectivity.
The project API returns the configured environment variable names, never values
resolved from those variables.

MCP calls require approval by default. Only an explicit per-tool override in
Plico's approval config can waive that default. A global default of `"none"` and
server annotations cannot waive MCP approval.
MCP results, server tool descriptions and input schemas are untrusted content,
including any instructions they contain; they cannot change approval policy.
Discovery preserves descriptions and schemas as metadata, not as permissions.
The adversarial eval follows in the final slice of this epic.

### Discover configured tools

```ts
import { loadProject } from "@plico-ai/core";
import { discoverMcpTools, loadProjectEnv } from "@plico-ai/runtime";

loadProjectEnv("."); // Optional: read this project's .env into the host environment.
const tools = await discoverMcpTools(await loadProject("."), { timeoutMs: 10_000 });
```

Discovery uses the official MCP client with automatic protocol negotiation for
both transports. For stdio, that can start a short-lived probe process before
the discovery process; server startup must tolerate this. It returns metadata,
then closes its clients, stdio processes and HTTP sessions before resolving.
It never calls a tool. All pages of the
server's tool list are checked against the exact allowlist; an unavailable
allowlisted tool is an error. An empty allowlist returns no tools from that server.

Each result includes `serverId`, the original `toolName`, `source`, `name`,
`description`, `inputSchema`, `capabilities` and `approval`. The Plico name is
`mcp_<server>__<tool>`: the tool portion is lowercased and characters outside
`[a-z0-9_]` become underscores. Normalized names longer than 64 characters are
rejected; use a shorter server ID. Name collisions are errors. Remote schemas are
preserved, capabilities are empty and approval metadata is required regardless
of server annotations. Results have no handler or live client handle.

The client passes its standard process environment plus stdio's configured `env`
variables; other host secrets are not inherited. `headersEnv` values are sent only
as headers to the configured HTTP endpoint; redirects are rejected. Missing
variables fail before connecting to that source. Resolved credential values and
raw server error bodies are not included in discovery errors or metadata.
Failures retain safe spawn codes, HTTP statuses or MCP error codes when available.

`timeoutMs` sets a positive deadline per source (30 seconds by default). Sources
are tried one after another, so this is not a deadline for the whole call. Pass an
`AbortSignal` as `signal` to cancel discovery. Cleanup also runs on failures and
cancellation. A source failure rejects the call instead of returning a partial
list. Projects without configured sources return `[]`. Existing project loading,
validation and TypeScript tool discovery remain offline. Ordinary dry runs and
mocked scripts also remain offline.
HTTP session termination has its own deadline of at most one second; stdio cleanup
uses the official client's process shutdown and kill escalation and can take a
few extra seconds beyond the source deadline.

### Execute configured tools

Provider-backed runs discover allowlisted MCP tools and combine them with the
project's TypeScript tools. Live scripted calls discover the sources they use.
Provider discovery runs sources in parallel and skips unavailable servers,
recording a `run.warning` event with the server ID and safe failure reason.
Healthy sources remain available to the conversation. Explicit discovery remains
strict and sequential; scripts fail if a source they explicitly call is unavailable.
`mcp_` is allowed in TypeScript tool names; an actual normalized-name collision
fails with both sources identified.

Arguments are validated against the remote input schema before approval or
execution. To waive approval for a specific read tool, use its normalized name:

```ts
approvals: {
  tools: { mcp_tickets__get_ticket: "none" },
},
```

Unlike a TypeScript tool's explicit requirement, MCP's default approval gate may
be waived by that per-tool override. Use narrow server allowlists and grant only
the credentials each server needs.

Discovery connections close before a run waits for approval. An approved call
opens a new connection (a new process for stdio), checks the tool description and
input schema against the recorded metadata, then calls the original server tool
name. Servers that require client session state across calls are unsupported in
this slice. The connect/list/call sequence shares the server's `callTimeoutMs`
deadline, defaulting to 30 seconds. Sessions and stdio processes close after
each call, including failures and cancellation; stdio shutdown can take a few
extra seconds. Cancellation cannot undo work already performed by the server.

Results enter the normal `tool.result` event and model conversation as
`{ content, structuredContent?, isError? }`. A server's `isError` result is retained
as untrusted tool data. Protocol failures contain safe codes instead of server
error text or response bodies. Known failures are journaled so resuming a later
approval wait does not repeat a failed call. Plico does not automatically retry;
a model may request another call, which is checked against approval policy again.

Completed calls replay from the journal without reconnecting. A crash after a
call's intent is recorded but before its outcome is journaled fails the pending
call by default with an unknown-outcome diagnostic. It makes no second remote
call; inspect the server before starting another call. Configure a server's
`replayOnCrash: ["get_ticket"]` before starting a run to opt that specific tool into
crash replay. This opt-in provides **at-least-once** delivery and requires idempotent
operations or server-side deduplication. Changes to MCP source config or approval
policy fail recovery before another call; reordering keys alone does not.
Changed remote descriptions or input schemas also
fail the pending call before execution.

The stricter recovery fingerprint also pins approvals for TypeScript-only projects.
Waiting runs saved with tool-only fingerprints or no fingerprint fail recovery after upgrading,
even if the project is unchanged. Finish those waits before upgrading or restart
them afterward.

For offline scripted evals, `mockTools: true` uses each step's supplied `result`
without connecting or resolving credentials; `live: true` opts that step into
execution. Offline mocks check the allowlist and approval policy, but do not
validate against a remote input schema.

### Check readiness and inspect tools

`plico readiness` connects to each configured server, lists its tools and reports an
`mcp.<serverId>` diagnostic. The check reports a missing allowlisted tool or an
unreachable server without throwing; projects without MCP sources make no new
connections. Readiness runs use a five-second probe deadline per server.

Studio's **Tools** view lists declared and MCP tools with their source and effective
approval policy. For MCP tools it shows the server and original tool name. The same
metadata is available to hosts at `GET /v1/tools`; this endpoint does not connect to
MCP servers or resolve credentials.

## Input schemas

Declare `inputSchema` with Zod 4 or JSON Schema. A project on `zod` 3.25 can import from `"zod/v4"`; Zod 3 schemas are rejected. Plico validates tool calls
with that schema and sends JSON Schema to the model. Parsed Zod values, including
defaults and transforms, reach the handler.

<Callout>Add `zod` to the project dependencies before importing it from a tool.</Callout>

Validation rejects duplicate names declared across `.tool.ts` files, and readiness
reports the duplicate under tool discovery.

## When a tool call fails

In a run with a real model, a bad tool call does not end the run at once. An unknown tool
name, arguments that fail `inputSchema`, or a handler that throws is returned to the model as
the tool result, `{ "error": "<message>" }`, and the event log records it as a `tool.result`.
The model can then correct the call. This matters most for small local models, which often
send numbers as strings.

A run allows 2 such failures. The third ends the run with the original error, in the same
`run.error` event as before. Scripted runs (`plico run --dry --script`) and approval denials
still fail immediately.

## Writing artifacts

A tool can read, write, and list artifacts with `ctx.artifacts`: `read(path)`,
`write(path, content, { mimeType })`, and `list()`. See [Artifacts](/docs/artifacts).

## Host context

When a host app starts a run with a `context` (see [Threads](/docs/threads#host-data-metadata-and-context)),
the handler receives it as `ctx.context`, such as `{ userId: "u-1" }`. It is `undefined` when
the host passed none, and it is the same value after a restart. Plico records it in the run's
event log, so keep secrets out of it and look them up inside the tool.
