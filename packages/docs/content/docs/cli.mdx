Run `plico --version` to print the installed version. Every command takes an optional project `[path]` and defaults to the current folder.

| Command | What it does |
| --- | --- |
| `plico validate [path]` | Validates a project and prints diagnostics. |
| `plico run [--message <text>] [path]` | Runs the agent with its configured model. |
| `plico run --dry [--persist] [--script <file>] [path]` | Runs with a scripted model, so it needs no key. |
| `plico runs [path]` | Lists saved runs. |
| `plico events <run-id> [--after <sequence>] [path]` | Prints a run's event log. |
| `plico cancel <run-id> [path]` | Cancels an active persisted run. |
| `plico eval [path]` | Runs the project's scripted evals. |
| `plico readiness [path]` | Reports readiness diagnostics. |
| `plico serve [path]` | Starts the HTTP API. |

`plico <command> --help` prints that command's usage.

Common flags: `--json` prints machine-readable output, and `--db <path>` points at a database other
than `.plico/plico.sqlite`. `plico run` without `--dry` needs a configured model; see
[Model providers](/docs/providers). A dry run prints its events but only saves them with
`--persist`.

## Scripts

`plico run --dry --script <file>` replays a script instead of calling a model. A script is a JSON
array of steps:

```json
[
  { "type": "assistant.output", "content": "I will create the ticket." },
  { "type": "tool.call", "toolName": "create_ticket", "arguments": { "title": "VPN down" },
    "result": { "ticketId": "T-1" } },
  { "type": "artifact.write", "files": [{ "path": "summary.md", "content": "# Ticket" }] }
]
```

| Step | Fields |
| --- | --- |
| `assistant.output` | `content`, the text the agent says. |
| `tool.call` | `toolName`, `arguments`, and an optional `result` used instead of running the handler. Add `"live": true` to run the real handler. |
| `artifact.write` | `files`, each with `path`, `content` and an optional `mimeType`. |

A script that calls a tool needing approval stops with `run.waiting`, prints
`Dry run waiting for approval.` and exits with code 2. Add `--persist` to save the run and print its
id. See [Approvals](/docs/approvals#try-it-without-a-key) for how to decide it.

An eval case is the same array, or an object with the array under `script` plus `description` and
`expect`, described next.

## serve

`plico serve --studio <project>` also serves the bundled Studio. `--host` and `--port` choose the
address; the default is `127.0.0.1:3000`. Other options:

- `--allow-remote` exposes the server on another host. See [HTTP API](/docs/http-api).
- `--allow-script` lets API callers send scripted runs. Their tool steps use the output in the script and never run handlers. See [HTTP API](/docs/http-api).
- `--inspect` serves for inspection beside a backend that owns the database: nothing is recovered or resumed and every change is refused. See [Use Plico from your backend](/docs/backend).

## eval

Each `evals/*.script.json` file is one case: a [script](#scripts) of steps, or an object with a
`script` array, an optional `description` and an optional `expect` (`status`, `outputContains`). A new
project has one case, `evals/smoke.script.json`, so `npm run eval` passes out of the box. `plico eval` exits 1 when a case fails, and also when there are
no cases, so a CI gate cannot pass with nothing tested. `--allow-empty` accepts an empty
`evals/` folder.

Evals never run tool handlers by surprise. A `tool.call` step supplies the tool's output as
`result`, and the run uses it instead of calling the handler:

```json
{ "type": "tool.call", "toolName": "create_ticket", "arguments": { "title": "VPN down" },
  "result": { "ticketId": "T-1" } }
```

A `tool.call` step without `result` fails the case and names the tool. Add `"live": true` to a
step to run the real handler on purpose. Approval policy still applies in evals, so a tool that
requires approval is held exactly as it is in a normal run.

### Turn a run into a case

`plico eval --from-run <run-id> [--name <name>] [path]` writes a stored run to
`evals/<name>.script.json` (the name defaults to the run id). Each tool call keeps the output it
produced as `result`, and `expect` records the run's status and final output. It refuses to
overwrite an existing case and fails on an unknown run id. Files a tool wrote are not carried over.

## Help and unknown flags

`plico validate --help` shows validation usage. Unknown flags are reported as errors.
`plico runs` reports clearly when a project has no saved runs.
