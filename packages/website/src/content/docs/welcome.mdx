title: Welcome to Plico
---

Plico is a **TypeScript-first agent app kit**. A folder of Markdown instructions,
skills, TypeScript tools, config, evals, memory, and artifacts becomes a runnable,
inspectable agent app.

Tools are loaded from their `.tool.ts` files. They can import sibling TypeScript
modules and npm packages installed in the project. `create-plico` includes a
`package.json` with `type: "module"` for ESM tool imports. Declare `inputSchema`
with Zod 3, Zod 4, or JSON Schema; Plico validates tool calls with that schema
and sends JSON Schema to the model. Parsed Zod values, including defaults and
transforms, reach the handler. Add `zod` to the project dependencies before
importing it from a tool.

Wrap a tool in `defineTool` and the config in `defineConfig`, both from `plico`,
to get editor types. `defineTool` infers the handler `input` from `inputSchema`.
Both helpers return their argument unchanged, and Plico finds them without a
`node_modules` in the project.

Plico needs Node 22.18 or later.

## Why Plico?

Most agent frameworks lock you into an SDK, a provider, or a runtime. Plico starts
from a different premise: **your agent should be a folder of files** — readable,
version-controllable, reviewable alongside your app code.

## Core Principles

- **File-first.** The project model is a directory tree. No black boxes, no hidden
  state. Everything is a file you can read, edit, and commit.
- **Event-native.** Every run produces a replayable canonical trace. Studio, evals,
  artifacts, and streams all derive from that one log.
- **Provider-agnostic.** Adapters map provider shapes to the project contract. Swap
  models and providers without rewriting your agent.

## Inspect and approve runs

Start the bundled Studio with `plico serve --studio <project>`. Studio shows the
run's event history and, when a tool call needs approval, its reason and input
arguments. Approve the call to resume the run or deny it to stop the run before
the tool executes. Each decision is recorded in the run's event log. The run
inspector also lets you cancel active runs. In Chat, replies stream in as
Markdown, **Stop** cancels the reply in progress, and **Inspect run** opens the
reply's timeline, where streamed model chunks are grouped into one row. The Readiness view reports approval
policy overrides that reference missing tools or conflict with a tool's declared
approval requirement. It also reports whether model-facing artifact tools are
configured as `read-write`, `read-only`, or `off`.

The server has no authentication, so it listens on loopback only and refuses
requests a web page could send. A foreign `Host` header (DNS rebinding) gets
421, a cross-origin `Origin` gets 403, and a request body that is not
`application/json` gets 415. Clients that send no `Origin`, such as curl and
the CLI, are unaffected. `plico serve --allow-remote` exposes the server on
another host and skips the `Host` check; the `Origin` check still applies. A host
app that mounts `createPlicoServer` under its own name passes
`allowRemote: true` and owns authentication. `Origin` must match in scheme,
host and port, so behind a TLS proxy the host app also passes
`publicOrigin: "https://its.host"`.

Cancel an active persisted run from the command line with
`plico cancel <run-id> <project>`, or send `POST /v1/runs/<run-id>/cancel` to the
server. Pressing Ctrl+C during `plico run` also cancels that run.

Artifact writes from TypeScript tools use `ctx.artifacts`. A tool can call
`read(path)`, `write(path, content, { mimeType })`, and `list()`. Writes accept
text or `Uint8Array` content and are staged with the durable tool step, so a
recovered run reuses its recorded write rather than executing it twice. Plico
stores content bytes once per SHA-256 hash in SQLite; text remains readable as
text, and binary event content uses a tagged base64 value on JSON surfaces.
Write paths must be relative, contain no `..`, and be at most 1,024 characters;
each write is limited to 1 MiB. A `Uint8Array` returned from a tool is encoded
as tagged base64 in its result event.
Workspace responses expose the latest files and an ordered version receipt
history for each run.
Compare two writes with
`GET /v1/runs/<run-id>/workspace/diffs?path=<path>&fromVersion=1&toVersion=2`.
Diffs accept text, JSON, and XML artifacts up to 1 MiB per version; binary or larger
versions are rejected. Binary files can be written and exported byte for byte.
Download a file from a run with
`GET /v1/runs/<run-id>/workspace/exports?path=<path>`. The response is an attachment
with the stored artifact content and media type.
In Studio, open a run's **Artifacts** view to preview files, compare stored versions,
and download the current workspace file.

Thread runs share one ordered artifact workspace. `GET /v1/threads/<thread-id>/workspace`
returns its current files and versions; every version identifies the writing run.
A run workspace includes files inherited from earlier turns and shows the state
as of that run. Diffs and exports work across those thread versions, and Studio's
Artifacts view labels thread workspaces and shows each version's writing run.

Threads get a `title` once the conversation has a topic. After each of a
thread's first three replies, Plico names it from the words the user used, so a
greeting such as "Hi" leaves it untitled until there is something to name. The
rule runs locally with no model call, and the assistant's text can only confirm a
topic, not add one. `PATCH /v1/threads/<thread-id>` with `{ "title": "..." }` (up
to 200 characters) renames a thread; a title set that way is never replaced.
Studio shows titles in the thread list and the chat header, where a pencil icon
renames the conversation.

Provider-backed runs have four built-in tools for this workspace: `list_files`,
`read_file`, `write_file`, and `edit_file`. Set `artifacts.access` in
`plico.config.ts` to `read-write`, `read-only`, or `off`; it defaults to
`read-write`. Read-only mode offers listing and reading. Off hides all four
model-facing tools while leaving `ctx.artifacts` available to trusted project
TypeScript tools. These tool names are reserved.

`list_files` accepts `*`, `**`, `?`, and comma-separated brace alternatives
(for example `reports/*.{md,txt}`). It returns paths in sorted, paginated order
(100 files per page by default). `read_file` uses a 1-indexed line offset,
defaults to 200 lines, and limits text output to 32 KiB per call. Binary files
return metadata without their bytes. `write_file` creates or overwrites text,
infers MIME type from the extension, and allows an explicit `mimeType` override.
`edit_file` replaces exact text and requires one match unless `replaceAll` is
true. Both model-facing write tools use the staged workspace path and enforce a
1 MiB content limit.

Use `plico validate --help` to show validation usage. Unknown flags are reported
as errors, and `plico runs` clearly reports when a project has no saved runs.
Validation rejects duplicate names declared across `.tool.ts` files, and readiness
reports the duplicate under tool discovery.

A `script` in a run request calls project tools with arguments the caller picks
and skips the model, so the API answers 403 `run.script_disabled` unless the
server starts with `plico serve --allow-script` (`allowScript: true` for
`createPlicoServer`). `plico run --dry --script` on the command line is unaffected.
